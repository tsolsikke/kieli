# Kieli の初版の設計(案)

この文書は、Kieli の初版(第 1 段階)の設計の案です。項目ごとに、案と、その良い点・悪い点、推奨、運用者の判断が要るかを書きます。
「推奨」は書き手の推奨で、運用者が採ったものではありません。運用者が決めたら、その項目を「決定」に書き換え、決めた日を添えます。

## 0. この文書の前提

### 0.1 決まっていること(運用者の決定。2026-10-24、「案 D」)

- Wayland の上では、Kieli は別のプロセスの IME として、標準の input-method-v2(と virtual-keyboard-v1)でコンポジタにつなぐ。Kieli 専用のプロトコルは作らない。
- ほかの OS には、kieli-core の上に、OS ごとの接続層を作る(将来の Windows 11 の TSF など)。
- crate の構成:
  - kieli-core:`no_std` + `alloc`。変換の規則と状態を持つ。Wayland・fd・serial・COM・描画・OS 固有のキーコードを持ち込まない。
  - kieli-cli:kieli-core の最初の利用者(ホストの端末で動く)。
  - kieli-wayland:第 2 段階で足す(このリポジトリの別の crate)。
  - 将来:Windows の TSF の接続層。
- 段階:
  - 第 1 段階:kieli-core と kieli-cli で、ローマ字からひらがなへの変換と、編集・確定・取消。これを「Kieli の初版の完成」と判定する。
  - 第 2 段階:kieli-wayland と、Linux の上の Seinas との統合。「Seinas との統合の完了」として別に判定する。
  - 第 3 段階以降:辞書・かな漢字変換・候補ウィンドウ。TSF はさらに後。
- 最初に保証する範囲は、Linux と ZeikOS の上の Seinas。

Seinas の ADR 0004 にある運用者の決定 K1〜K9(2026-10-14)のうち、この文書に関わるもの:Rust で一から作り、外のコードはコピーしない(K1)、ふつうのローマ字入力とかな漢字変換を目指す(K2)、初版はローマ字からひらがなへの変換だけ(K5)、Kieli の本体は Smithay に依存させない(K9)。

## 1. ローマ字の規則

### 1.1 事実

- JIS X 4063:2000(仮名漢字変換システムのための英字キー入力から仮名への変換方式)で、ローマ字入力は 2000 年に標準化されたが、2010 年 1 月 20 日に廃止された [WP]。
- その規格の表では、「ん」は `n`・`n'`・`nn`、「っ」は `xtu` と「子音字を重ねる ただし『nn』は『ん』」、小書き文字は `xa`・`xi`・`xu`・`xe`・`xo`、`xya`・`xyu`・`xyo`、`xwa`、`xka`・`xke` の `x` の形 [WP]。
- 「`la` で『ら』を出す実装と『ぁ』を出す実装があった場合、規格から外された」[WP]。そのため `l` の形は規格に無い。
- Mozc のテーブルは、タブで区切った 3 列(入力、出力、出力の後に残す入力)[Mozc]:
  - `nn` → ん、`n'` → ん、`n` → ん、`xn` → ん。
  - 促音は、子音を重ねた行の 3 列目に、重ねた子音を残す形(`kk` → っ、残り `k`。`tt`、`ss`、`cc` も同じ。`tch` → っ、残り `ch`)。
  - 小書き文字は、`x` の形と `l` の形の両方がある(`xa`/`la` → ぁ、`xtu`/`ltu`・`xtsu`/`ltsu` → っ、`xya`/`lya` → ゃ、`xwa`/`lwa` → ゎ)。`xka`/`lka` は、カタカナの「ヵ」を出す(ひらがなの「ゕ」ではない)。
  - `n` の後に子音が来たとき(`nk` など)の扱いは、テーブルには書いていない。テーブルを読む側の振る舞いで決まる(推測。確かめていない)。

### 1.2 変換のしかた(案)

未確定文字は、「かなになった部分」と「まだかなにならないローマ字(保留)」に分けて持ちます。キーで文字が来るたびに、保留の後ろに足し、テーブルと照らします。

- 保留が、テーブルのどれかの入力と一致し、ほかの入力の頭の部分にもならなければ、出力に置き換える(3 列目があれば、それを新しい保留にする)。
- 保留が、テーブルのどれかの入力の頭の部分なら、次の文字を待つ。
- どれの頭の部分にもならなければ、「未定義の綴り」(1.6)として扱う。

テーブルは、Kieli の側で一から書きます。Mozc のテーブルは、振る舞いを比べるために使うだけです。テーブルは変わらないデータ(`static` の定数)として持ちます。これは大域の「状態」ではありません(8.3)。

### 1.3 「ん」(n・nn・n')

| 案 | 内容 | 良い点 | 悪い点 |
| --- | --- | --- | --- |
| A | `nn` → ん、`n'` → ん。`n` の後に、母音・`y`・`n`・`'` のほかの文字が来たら、ん を出して、その文字を保留に残す。保留が `n` だけのまま確定したら ん | JIS X 4063 の表と Mozc のテーブルの両方と合う。`kanji` → かんじ のように、`n` を重ねずに打てる | `nna` は「んあ」になる(「んな」は `nnna`) |
| B | A に加えて、`nn` の後に母音が来たら「んな」行にする | `nna` → んな と打てる | `nn` で ん を出した後に、出したものを打ち消すことになり、規則が複雑になる。JIS と Mozc のどちらとも違う |
| C | `nn` と `n'` だけで ん を出す(`n` + 子音を扱わない) | 規則がいちばん簡単 | `kanji` が打てず、ふつうの使い方と違う |

推奨:案 A。`xn` → ん は、Mozc にはあるが JIS の表には無い [WP][Mozc]。入れても害が無いので、入れる案にします。

運用者の判断:要らない(案 A を初版の規則として書く)。ただし、`nna` を「んな」にしたい場合は、案 B を指示してください。

### 1.4 促音(っ)

| 案 | 内容 | 良い点 | 悪い点 |
| --- | --- | --- | --- |
| A | `n` のほかの同じ子音を重ねたら、っ を出して、後の子音を保留に残す。`tch` → っ + `ch` も入れる | JIS の規則と Mozc のテーブルと合う | `mm` も っ になる(「っま」) |
| B | A から `m` を外す(`mm` は ん + `m`) | 「ん」と「っ」を打ち分けたい人には分かりやすいかもしれない(推測) | どの IME がこう振る舞うかは確かめていない |

推奨:案 A。重ねる子音は `k g s z t d h b p f j c q v w r y m` とし、`l` と `x` は小書き文字に使うので入れません(`ll`・`xx` は未定義の綴り)。Mozc のテーブルに、どの子音の重ねが入っているかの全部は確かめていません(`kk`・`ss`・`tt`・`cc`・`tch` は確かめた [Mozc])。テーブルを書くときに、子音ごとにテストを置きます。

運用者の判断:要らない。`mm` の扱いだけ、案 B にしたければ指示してください。

### 1.5 小書き文字(x と l)

| 案 | 内容 | 良い点 | 悪い点 |
| --- | --- | --- | --- |
| A | `x` の形と `l` の形の両方 | Mozc のテーブルと合う。どちらで打つ人も困らない | `la` を「ら」と思う人には合わない(JIS が `l` の形を外した理由 [WP]) |
| B | `x` の形だけ | JIS の表と合う | `l` の形に慣れた人が困る |

推奨:案 A。対象は ぁぃぅぇぉ、ゃゅょ、っ(`xtu`・`xtsu`)、ゎ、ヵ・ヶ(`xka`・`xke`)。

「ヵ」「ヶ」について:JIS の表はひらがなの「ゕ」「ゖ」(U+3095、U+3096)で、Mozc はカタカナの「ヵ」「ヶ」を出します [WP][Mozc]。「ゕ」「ゖ」はフォントに無いことがある(推測。Seinas の既定のフォントで確かめていない)ので、Mozc と同じカタカナを推奨します。

運用者の判断:要らない(「ゕ」「ゖ」にしたい場合だけ指示してください)。

### 1.6 未定義の綴り

保留が、テーブルのどの入力の頭の部分にもならないとき(`q` の後の `z` など)の扱い。

| 案 | 内容 | 良い点 | 悪い点 |
| --- | --- | --- | --- |
| A | 保留の先頭の 1 文字を、ローマ字のまま「かなになった部分」へ移し、残りを照らし直す | 打ったものが消えない。後で Backspace で直せる | 未確定文字に英字が混ざる |
| B | 保留の先頭の 1 文字を捨てる | 未確定文字がかなだけになる | 打ったキーが黙って消える |
| C | 足そうとした文字を受け付けない(キーは消費して何もしない) | 状態が壊れない | 打てないキーがあるように見える |

推奨:案 A。ローマ字のまま移す文字は、半角(打った ASCII のまま)にします。全角の英字にする形もありますが、幅の変換のテーブルが要るので、初版では入れません。

ほかのよく使う記号の扱い(案):ひらがなのモードでは、`-` → ー、`,` → 、、`.` → 。、`[` → 「、`]` → 」 をテーブルに入れます(一般的な振る舞い。Mozc のテーブルで確かめていない)。数字と、ほかの記号は、案 A と同じく半角のまま未確定文字に入れます。大文字の英字(Shift を押した文字)は、テーブルと照らさず、半角のまま未確定文字に入れます。

運用者の判断:要る。(1) 案 A でよいか。(2) 英字を半角のまま残すか、全角にするか。(3) 上の記号の一覧でよいか。

## 2. キーの動き

### 2.1 前提

- kieli-core が受けるのは、正規化したイベント(8.4 の `Event`)です。物理のキー(keysym、evdev の番号、端末のバイト列、Windows の仮想キーコード)からイベントへの変換は、接続層が行います。
- Ctrl・Alt・Super を押したままのキーは、接続層が `Event::Other` にします(文字にしない)。
- 消費しなかったキーは、接続層がアプリへ渡します(Wayland では virtual-keyboard で戻す [Seinas])。消費したキーは、アプリへ渡しません。文字を出さずにキーを消費するのは、ふつうの IME の振る舞いで、Seinas もキーごとの返事を求めません [Seinas]。
- キーの繰り返しは、接続層が同じイベントを繰り返して送ります。kieli-core は時刻とタイマーを持ちません。

### 2.2 キーごとの動き(案)

「未確定文字あり」は、かなになった部分か保留のどちらかが空でない状態です。モードは、ひらがなと直接入力の 2 つ(7 を参照)です。

| イベント | 未確定文字なし | 未確定文字あり |
| --- | --- | --- |
| 文字(ひらがなのモード) | 消費する。未確定文字を始める | 消費する。未確定文字に足す |
| 文字(直接入力のモード) | 消費しない(アプリへ渡す) | (起きない。モードを変えるときに未確定文字を片付けるため) |
| Backspace | 消費しない | 消費する。保留があれば保留の最後の 1 文字、無ければかなの最後の 1 文字(Unicode のスカラー値 1 つ)を消す。全部消えたら「未確定文字なし」に戻る |
| Enter(確定) | 消費しない | 消費する。未確定文字を確定する。保留が `n` だけなら ん にし、ほかの保留はローマ字のまま確定する。Enter そのものはアプリへ渡さない |
| Esc(取消) | 消費しない | 消費する。未確定文字を全部捨てる。何も確定しない |
| モードの切り替え | 消費する。モードを変える | 消費する。未確定文字を確定してから、モードを変える(下の案) |
| Space | 消費しない | 消費して何もしない(下の案) |
| その他(矢印・Tab・Ctrl の組み合わせなど) | 消費しない | 消費して何もしない(下の案) |

Backspace は、「きゃ」の後なら「ゃ」だけを消して「き」を残します(1 文字ずつ)。保留の英字も 1 文字ずつ消します。

Enter を消費してアプリへ渡さないのは、日本語の IME の一般的な振る舞いです(確定の Enter で改行しない)。

### 2.3 判断の要る所

モードの切り替えのとき、未確定文字があったら:

| 案 | 内容 | 良い点 | 悪い点 |
| --- | --- | --- | --- |
| A | 確定してから切り替える | 打ったものが残る | 意図しない確定になることがある |
| B | 捨ててから切り替える | 確定が起きない | 打ったものが消える |
| C | 未確定文字を残したまま切り替える | 続けて打てる | 直接入力のモードで未確定文字がある状態ができ、表の行が増える |

推奨:案 A。

未確定文字があるときの Space:

| 案 | 内容 | 良い点 | 悪い点 |
| --- | --- | --- | --- |
| A | 消費して何もしない | 第 3 段階で、Space をかな漢字変換に使うときに、振る舞いの変わり方が小さい | 初版では、Space が効かないように見える |
| B | 確定してから、空白をアプリへ渡す | 英文のように打てる | 第 3 段階で振る舞いが変わる |
| C | 未確定文字に空白を足す | 打ったとおりに残る | 同上 |

推奨:案 A。

未確定文字があるときの、その他のキー(矢印・Tab・Ctrl の組み合わせなど):

| 案 | 内容 | 良い点 | 悪い点 |
| --- | --- | --- | --- |
| A | 消費して何もしない | 未確定文字があるときに、アプリへ思わぬキーが届かない | Ctrl+S などが効かない。矢印で未確定文字の中を動けない |
| B | 確定してから、キーをアプリへ渡す | 打ちながらショートカットが使える | Wayland では、確定の文字(input-method の commit)とキー(virtual-keyboard)が別のオブジェクトで届くので、アプリでの順が保たれるかを確かめていない(推測) |
| C | 確定せずに、キーだけをアプリへ渡す | 簡単 | アプリの状態と未確定文字がずれる |

推奨:案 A。初版では、未確定文字の中のカーソルは持たず、いつも未確定文字の終わりに置きます(4 を参照)。

切り替えのキーは、接続層が決めます(jp106 の半角/全角など。英字配列での組み合わせは、第 2 段階の前に決める [Seinas] の Q7)。

運用者の判断:要る。(1) 切り替えのときの未確定文字(推奨 A)。(2) Space(推奨 A)。(3) その他のキー(推奨 A)。(4) 未確定文字が無いときの Space を、アプリへ渡す(半角の空白になる)でよいか。

## 3. 未確定文字を持ったまま入力先を失った場合

### 3.1 事実(Wayland)

- コンポジタは、フォーカスが変わると、IME に deactivate と done を送る [Seinas](`docs/ime.md` の「フォーカスが変わったとき」)。
- inactive の間に IME が送った要求は、コンポジタが受け付けるが、serial の決まりと activate でのリセットのため、次の入力先には効かない [IM] 66〜68 行。Seinas は、deactivate の後の要求をどのアプリにも届けない [Seinas]。
- アプリは、text-input の leave を受けたら、未確定文字を消す(「The client should reset any preedit string previously set」[TI] 349〜351 行)。Seinas は、空の未確定文字を IME の代わりに送らない [Seinas]。
- activate は、それまでの状態を全部リセットする [IM] 81〜84 行。activate には、どの入力欄かを示す引数が無い。そのため、IME は、戻ってきた入力先が前と同じ欄かを知る手段を持たない。

### 3.2 案

| 案 | 内容 | 良い点 | 悪い点 |
| --- | --- | --- | --- |
| A | 取り消す(捨てる) | 仕様の振る舞い(leave でアプリが消す)と合う。古い入力先へ文字が入ることが無い | 打ったものが消える |
| B | 失う前に確定する | 打ったものが残る | Wayland では、deactivate を受けた時点で、もう前の入力先へ届かない。確定を先に送る機会が IME に無い |
| C | 残しておき、同じ入力先に戻ったら戻す | 打ったものが残る | Wayland では、同じ入力先かを知る手段が無い(3.1) |

推奨:案 A。kieli-core は、取り消す操作(`Session::cancel`)と確定する操作(`Session::commit`)の両方を持ち、入力先を失ったときにどちらを呼ぶかは、接続層が決めます。kieli-wayland では、deactivate を受けたら `cancel` を呼び、何も送りません。将来の TSF の接続層では、確定する形も選べます(Windows の振る舞いは確かめていない)。

運用者の判断:要る(初版は取り消す案でよいか)。

## 4. 文字位置の単位と、文字境界の保証

### 4.1 事実

- input-method-v2 の文字は UTF-8 で、位置と長さはバイトで数える [IM] 38 行。`set_preedit_string` の `cursor_begin`・`cursor_end` もバイトで、両方 -1 ならカーソルを隠す [IM] 239〜242 行。
- text-input-v3 の位置は、コードポイントの途中のバイトを指してはならない(先頭のバイトか、バッファの終わりを指す)[TI] 61〜63 行。
- Windows の TSF の文字位置(ACP)は、UTF-16 の単位(WCHAR)で数える、と書き手は理解しているが、Microsoft Learn のページで確かめられていない(2026-10-25 に読もうとした 2 つの URL がどちらも見つからなかった)。TSF の接続層を作るときに確かめます。

### 4.2 案

| 案 | kieli-core の持ち方 | 良い点 | 悪い点 |
| --- | --- | --- | --- |
| A | UTF-8 の `String` と、バイトの位置 | Rust の `str` のまま扱える。Wayland へ変換なしで渡せる | TSF では、UTF-16 の位置へ変える手間が要る |
| B | `char`(スカラー値)の数 | OS の単位に依らない | どの接続層でも変換が要る |
| C | UTF-16 | TSF へそのまま渡せる | Rust の文字列と合わず、kieli-core の中のすべての所で変換が要る |

推奨:案 A。

- 位置は、kieli-core の中で、文字境界にある値だけを作れる型(8.4 の `Preedit` の `cursor`)で返し、作るときに `str::is_char_boundary` で確かめます。テストでも確かめます。
- Wayland の接続層は、バイトの位置を `i32` にして、そのまま渡します(長さの上限(5)が 4000 バイトより小さいので、`i32` に収まる)。
- UTF-16 の位置へ変える関数(`utf16_offset(text, byte_pos)` のような、OS の型を使わない純粋な関数)は、kieli-core に置いてよい案にします。TSF の接続層ができるまでは作りません。
- かなはどれも基本多言語面にあるので、UTF-16 で 1 単位です。将来の辞書でサロゲートペアになる文字(「𠮷」など)が入ると、UTF-8 と UTF-16 の位置の差が大きくなるので、変換の関数にはその場合のテストを置きます。
- Kieli は、濁点を結合文字(U+3099)で出さず、合成済みの文字(「が」など)を出します。そのため、Backspace を Unicode のスカラー値 1 つずつにしても、かなの見た目が崩れません。

初版では、未確定文字の中のカーソルは、いつも未確定文字の終わりです(`cursor_begin` = `cursor_end` = 長さ)。

運用者の判断:要らない。

## 5. 未確定文字の長さの上限

### 5.1 事実

- input-method-v2 の `commit_string` と `set_preedit_string` の文字は、Wayland のメッセージの上限のため、4000 バイトより長くできない [IM] 216 行、237 行。
- ひらがなは UTF-8 で 3 バイトなので、4000 バイトはひらがなで 1,333 文字(計算)。

### 5.2 案

| 案 | 内容 | 良い点 | 悪い点 |
| --- | --- | --- | --- |
| A | kieli-core に上限を持たず、接続層が切る | kieli-core が簡単 | 接続層ごとに、上限を越えたときの振る舞いがばらばらになる |
| B | kieli-core に、UTF-8 のバイト数の上限を持つ(セッションを作るときに設定で渡す) | どの接続層でも同じ振る舞いになる。Wayland の上限と直に比べられる | — |
| C | kieli-core に、文字数の上限を持つ | 人に分かりやすい | Wayland の上限と比べるのに、最悪のバイト数の計算が要る |

推奨:案 B。既定の上限は 1,024 バイト(ひらがなで 341 文字。4000 バイトに余裕を持たせた値で、根拠のある値ではない)。上限を越える文字が来たら、キーを消費して何もしない(未確定文字を変えない)。上限に達したときに自動で確定する形は、思わぬ確定になるので採りません。保留のローマ字の長さは、テーブルのいちばん長い入力(`xtsu` などの 4 文字)で抑えられるので、別の上限は要りません。

運用者の判断:要る。(1) 既定の上限の値(推奨 1,024 バイト)。(2) 越えたときに受け付けない(推奨)か、自動で確定するか。

## 6. パスワードなどの入力を残さない方針

### 6.1 事実

- text-input-v3 の content_hint の `sensitive_data` は「typed text should not be stored」、`hidden_text` は「characters should be hidden」[TI] 209〜210 行。content_purpose の `password`・`pin` は、`sensitive_data` と組み合わせる [TI] 240〜241 行。
- IME には、input-method-v2 の `content_type` イベントで、hint と purpose が届く。初期値は hint が none、purpose が normal で、done で効く [IM] 169〜181 行。activate の後、done の前に届く(アプリが対応していれば)[IM] 88〜90 行。
- Seinas は、ふだんのログに、生のキー・keysym・未確定文字・確定した文字・周りの文字を出さない [Seinas] ADR 0004 の 1.6。

### 6.2 案

kieli-core について(案):

- kieli-core は、ログを出す仕組みを持ちません(I/O を持たないので、出せない)。
- セッションに「残さない入力か」のフラグ(8.4 の `Session::set_sensitive`)を持たせます。初版には、履歴も学習も無いので、フラグを見る所はまだありません。第 3 段階で、変換の履歴や学習を入れるときは、このフラグが立っている間の入力を残さないことを、その段階の判定に入れます。

接続層について(案):

- 接続層は、`sensitive_data` に関係なく、ふだんのログに、キー・未確定文字・確定した文字・周りの文字を出しません(Seinas と同じ)。調べるためのログは、明示して付けるオプションのときだけにします。
- kieli-wayland は、`content_type` の hint の `sensitive_data`、または purpose の `password`・`pin` を受けたら、セッションのフラグを立てます。

パスワードの欄での変換のしかた:

| 案 | 内容 | 良い点 | 悪い点 |
| --- | --- | --- | --- |
| A | purpose が `password`・`pin` のときは、その activate の間は直接入力として扱う(キーを全部アプリへ渡す)。モードの値そのものは変えない | 未確定文字がアプリに見えない(`hidden_text` の欄で、未確定文字が見えてしまうことを避ける)。Windows でもパスワードの欄では IME が使えない形が一般的(推測。確かめていない) | パスワードにかなを使えない |
| B | ふだんどおり変換し、残さないだけ | かなのパスワードも打てる | 未確定文字が画面に出る |

推奨:案 A。`sensitive_data` だけが立っていて、purpose がパスワードでない欄では、ふだんどおり変換し、残さないだけにします。

運用者の判断:要る(パスワードの欄で直接入力にする案 A でよいか)。

## 7. 入力モードを全体共通にするか、入力先ごとに持つか

### 7.1 事実

- Seinas の ADR 0004 の 3 の「GPT-6 の推奨」に、「入力欄ごとに 1 つのセッション。モードと未確定の文字を、プロセス全体の状態に置かない」がある。これは運用者が採ったものではない [Seinas]。
- input-method-v2 の activate には、どの入力欄かを示す引数が無い(3.1)。そのため Wayland の IME は、入力欄を見分けて、欄ごとのモードを覚えることができない。

### 7.2 案

| 案 | 内容 | 良い点 | 悪い点 |
| --- | --- | --- | --- |
| A | モードは全体で 1 つ。未確定文字は、入力先(セッション)ごと | どの入力先へ移っても、モードが変わらず分かりやすい。Wayland でも作れる。タスクバーにモードを出すとき(K8)、出す値が 1 つで済む | アプリごとにモードを変えたい人には合わない |
| B | 入力先ごとにモードを持つ | アプリごとにモードを覚えられる | Wayland では入力先を見分けられないので、作れない |
| C | activate のたびに、決めたモード(たとえば直接入力)に戻す | 状態が残らず単純 | 移るたびに切り替え直す手間がある |

推奨:案 A。ただし、「全体で 1 つ」の値は kieli-core の大域の状態にはせず、接続層(kieli-wayland、kieli-cli)が 1 つ持ち、新しいセッションを作るときに渡します。kieli-core の中では、モードもセッションの状態の 1 つです(8.3)。未確定文字は、セッションごとに持ち、入力先を失ったら捨てます(3)。これで、上の GPT-6 の推奨のうち、未確定文字の部分は満たし、モードの部分だけが違う形になります。

運用者の判断:要る(初版は全体共通の案 A でよいか)。

## 8. kieli-core の境目

### 8.1 持ち込まないもの

- `no_std` + `alloc` にする。`std` を使わない。
- Wayland の型、fd、serial、COM、描画、OS 固有のキーコード(keysym、evdev の番号、Windows の仮想キーコード)を持ち込まない。
- 時刻とタイマー(キーの繰り返し)を持ち込まない(2.1)。
- ログと I/O を持たない(6.2)。

`tools/check.sh` が、kieli-core を std の無い target(`x86_64-unknown-none`)でビルドすることと、依存が `tools/core-deps.allow` の一覧の中だけであること(今は依存なし)を見張ります。

### 8.2 入力と結果

- 入力は、正規化したイベント(`Event`)で受けます。
- 結果は、「消費したか」「未確定文字」「確定文字」で返します(`Outcome`)。text-input-v3 では、未確定文字は done のたびに初期値(空)に戻る [TI] 380 行ので、接続層は、変わったときに限らず、今の未確定文字を毎回送る必要があります。そのため `Outcome` には、差分ではなく、今の未確定文字の全体を入れます。

### 8.3 状態の持ち方

- 入力セッションの状態(未確定文字、保留、モード、残さない入力かのフラグ)は、`Session` のインスタンスごとに持ちます。可変の大域の状態(`static mut`、`static` のセル、スレッドローカルなど)は使いません。
- ローマ字のテーブルのような、変わらないデータは `static` の定数にしてかまいません。

### 8.4 型と関数の形(下書き)

名前と形は下書きで、第 1 段階の実装で変わることがあります。

```rust
/// 入力モード。
pub enum InputMode {
    /// ローマ字をひらがなにする。
    Hiragana,
    /// 変換しない(キーをアプリへ渡す)。
    Direct,
}

/// 接続層が正規化したイベント。
pub enum Event {
    /// Shift を反映した後の文字。Ctrl・Alt・Super を押したままのものは Other にする。
    Char(char),
    Backspace,
    /// 確定(Enter)。
    Commit,
    /// 取消(Esc)。
    Cancel,
    Space,
    ToggleMode,
    SetMode(InputMode),
    /// それ以外のキー(矢印・Tab・Ctrl の組み合わせなど)。
    Other,
}

/// 未確定文字。cursor は UTF-8 のバイトの位置で、どちらも文字境界にある。
pub struct Preedit<'a> {
    pub text: &'a str,
    pub cursor: core::ops::Range<usize>,
}

/// 1 つのイベントを処理した結果。
pub struct Outcome {
    /// キーを消費したか。false なら、接続層はキーをアプリへ渡す。
    pub consumed: bool,
    /// 確定した文字(無ければ空)。
    pub commit: String,
    /// 処理した後の未確定文字の全体(無ければ空)。カーソルは終わりにある。
    pub preedit: String,
}

/// セッションを作るときの設定。
pub struct Config {
    pub mode: InputMode,
    /// 未確定文字の長さの上限(UTF-8 のバイト数)。
    pub max_preedit_bytes: usize,
}

pub struct Session { /* 未確定文字、保留、モード、フラグ */ }

impl Session {
    pub fn new(config: Config) -> Self;

    /// イベントを消費するかを調べる。状態は変えない(&self なので、型で保証される)。
    /// TSF の OnTestKeyDown のような使い方のためのもの。
    pub fn would_consume(&self, event: &Event) -> bool;

    /// イベントを処理して状態を進める。
    /// 同じ状態で would_consume(&e) と handle(e).consumed は、いつも同じ値になる。
    pub fn handle(&mut self, event: Event) -> Outcome;

    /// 入力先を失ったときなどに、未確定文字を捨てる。
    pub fn cancel(&mut self) -> Outcome;
    /// 未確定文字を確定する。
    pub fn commit(&mut self) -> Outcome;

    pub fn preedit(&self) -> Preedit<'_>;
    pub fn mode(&self) -> InputMode;
    pub fn is_composing(&self) -> bool;

    /// 残さない入力か(6)。
    pub fn set_sensitive(&mut self, sensitive: bool);
}
```

調べる操作と進める操作を分ける理由:Windows の TSF では、キーを処理するかを先に問い合わせる `ITfKeyEventSink::OnTestKeyDown` があり、`pfEaten` に「the key event would be handled」かを返す [TSF]。この問い合わせで状態を進めないように、`would_consume` を `&self` にします。`would_consume` と `handle` の判定は、同じ関数(状態とイベントから「消費するか」だけを決める内部の関数)から作り、食い違わないことを、イベントの並びを変えたテストで確かめます。

接続層の形(参考):

- kieli-cli:端末から読んだものを `Event` にし、`Outcome` を画面に出す。
- kieli-wayland:grab で届いたキーを keymap で keysym にして `Event` にし、`would_consume` を使わずに `handle` だけを呼ぶ。消費しなかったキーは virtual-keyboard で戻し、消費したら `set_preedit_string`・`commit_string`・`commit` を送る。
- TSF の接続層:`OnTestKeyDown` で `would_consume`、`OnKeyDown` で `handle` を呼ぶ。

運用者の判断:要らない(境目の決まりは、運用者の指示のとおり)。型と関数の形は、第 1 段階の作業の (2) が終わったところで見てもらいます。
